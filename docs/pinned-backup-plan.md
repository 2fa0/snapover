状态：入口已暂时下线（`cmd/snapover/window.go` 的 `historyPage` 中注释掉 `a.backupSettings(c)`）。历史层实现保留：`internal/history/backup.go` 的 `ExportPinned` / `ExportPinnedParts` / `ImportPinned`，以及 `cmd/snapover/history_backup.go` 的界面层与 i18n 文案。本文记录重做前要回答的问题和已知缺陷，不代表已有实现要全部推翻。

## 下线前的行为（供重做参考）

原界面通过「复制历史 → 置顶备份」提供 ZIP 导出／导入，保存置顶文本全文、图片和备注，不携带设备身份、信任记录、来源信息或文件正文。备份未加密。每份最多 100000 条、解压后的 JSON 合计最多 1 GiB，按最新到最旧的顺序导出全部置顶文本和图片，超限自动分卷。第一份使用选定文件名，其余在同目录生成带 `-part-002-*.zip` 等后缀的文件，随机后缀避免覆盖其他备份；导入时可一次选择全部分卷，每份也可在旧版本中单独导入。

导入追加记录并重新分配可用数字快捷键，不覆盖已有置顶，重复导入会产生新记录。损坏备份在写入前拒绝；磁盘或容量错误可能留下已完成的部分，界面报告已处理条数。导入遵守历史容量限制，可能清理未置顶内容。

## 1. 先要决定的定位

现有实现按“备份／恢复”设计，但置顶内容的实际价值更像“常用片段库”：带备注、带 `⌘1`–`⌘9` 数字快捷键。这两个定位要求的东西不同：

- **备份**：防丢失、可恢复到同一台机器，重点是完整性、版本兼容、增量。
- **片段库迁移／导入导出**：跨机器、可读、可手工编辑、可挑选，重点是格式和选择粒度。

重做前先确定服务哪一种，否则会出现“两边都沾一点、两边都不好用”的现状：ZIP 里是 JSON、导入只能全量追加、导出必须先有置顶、用户既不能只带走三条，也不能在别的工具里读。

决定项：保留／取消该功能；若保留，是“整库备份”还是“片段导出”。

## 2. 现有实现的具体问题

1. **只能全有或全无**：导入只能整个 ZIP 追加，不能选择某几条、不能合并去重、不能把导入结果设为未置顶。重复导入产生重复记录，且是新的置顶。
2. **格式不可读**：内容是 `0000.json` 一堆 JSON，用户没法打开看、没法编辑、没法 grep。文本类置顶本可以导出成 `.md` / `.txt` 目录，图片导出成同名 `.png`，一份“能看的备份”比一分“能导入的压缩包”有用得多。
3. **分卷是过度设计**：为了 1 GiB 上限写了自动分卷、`-part-002-*` 随机后缀、跨分卷导入提示（“导入时请选择所有分卷”）。这个上限现实中很难触发，却产生了最复杂的代码路径和最多的用户操作要求。若保留，先把上限与分卷一起砍掉，超限就明确报错让用户自己分批。
4. **未加密没有任何对策**：置顶里最容易出现的就是账号说明、内网地址、模板句。当前只有一行灰字提醒“请妥善保管”。至少要决定：导出前提示包含敏感内容条数、或导出默认脱敏／可选口令加密，或干脆坚持“不提供导出”这条产品决策。
5. **入口和文案的重心不对**：现在是一个折叠区，标题“置顶备份”加一句“按最新到最旧的顺序导出全部置顶记录”，下面还有一段说明分卷、追加、清理规则的长灰字。这些都在解释实现细节而不是用户收益，违反界面文案“布局说明一切”的约定。
6. **失败语义偏技术**：“磁盘或容量错误可能留下已完成的部分，界面报告已处理条数”这类行为应在设计上避免，而不是靠文案解释。导入应先构建好目标集再一次性提交，或提供回滚。
7. **没有迁移入口**：换机是这类功能最真实的场景，但“设置 → 打开数据目录”里没有一句话告诉用户可以整体拷贝 `history/` 目录。这个零成本的说明可能比整套 ZIP 更解决问题。

## 3. 重做时的验收点

- 明确目标用户与场景，写在 `docs/features_zh.md`（及英文版）里，一句话说清“为什么需要它”。
- 导入可控：可选条目、可去重、可导入为非置顶。
- 格式可读：文本可被外部工具打开；同时保留一份可完整还原的机器可读形式。
- 失败可回滚或明确无副作用，界面不需要解释半成品状态。
- 上限与分卷：要么删掉，要么用一句能说清的话表达；不要再为超大备份维护独立代码路径。
- 敏感内容有对策，而不只是一行提醒。
- 双语文案同步，`go test ./cmd/snapover ./internal/history` 覆盖新行为；改文案后跑 `go test ./cmd/snapover` 更新断言。
