# 代码审核与内存优化（2026-10-14）

审核覆盖当前未提交的文本上限、文本预览和 Finder 快速操作改动，并检查了连接与传输、CLI 服务生命周期、历史存储、搜索、缩略图缓存和窗口关闭路径。

## 修复的问题

| 功能 | 问题 | 处理 |
| --- | --- | --- |
| 连接关闭 | 已完成握手的 TLS 连接在关闭时会发送 close-notify；对端不读取时，关闭会等待，也可能延长引擎锁的持有时间 | 会话直接关闭底层传输，及时释放队列并解除阻塞；增加对端不读取时的回归测试 |
| 帧写入 | 底层写入不足且未返回错误时，发送仍返回成功 | 使用缓冲区的 WriteTo 检查短写，返回 io.ErrShortWrite |
| CLI 服务 | 显式 Close 后，等待父 context 取消的协程仍驻留 | 服务持有自己的可取消 context，Close 同时取消请求上下文和等待任务；增加回归测试 |
| 大文本阅读 | 只为超长单行分段，大型多行文本仍一次性创建完整编辑器 | 超过 256 KiB 的文本也分段显示，每段最多 16 KiB；保留复制全文，普通短文本仍可直接全选复制 |

## 可维护性

Windows「发送到」和 Finder「快速操作」共用安装、设置保存和失败回滚流程。平台文件保留各自的设置界面、启动条件和系统服务刷新，避免两份入口管理代码分别修改。

文本预览和全文阅读共用只读编辑器配置。文本上限仍由引擎统一执行，历史中的完整文本继续按需从磁盘读取，缩略图保持已有的数量和字节预算。

## 内存测量

以下为本机 Apple M4、macOS arm64 的单次操作累计分配量，不是应用常驻内存；测试范围不包含系统剪贴板和其他应用。

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 编码发送 20 MiB 文本帧，BenchmarkWriteLargeText，3 次 | 41,961,160 B/op（约 40 MiB） | 20,981,634 B/op（约 20 MiB） |
| 打开约 20 MiB 的多行代码文本，UI 测试 | 约 49.2 MiB | 约 0.7 MiB |

发送帧直接在同一个缓冲区内编码并填写帧头，去除了整帧的第二份复制。全文阅读只为当前段建立编辑器，关闭窗口仍释放文本和编辑器引用。
