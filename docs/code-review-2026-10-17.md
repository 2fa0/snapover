# Snapover 审计记录 · 2026-10-17

检查对象为本机当前工作区，包含尚未提交的“复制并同步”改动。仅审计，未修改产品代码。覆盖剪贴板采集、同步队列、历史存储、预览与粘贴、窗口生命周期、文件传输及本地 CLI；同时阅读了本地 MyGo v0.5.5 的相关实现。

结论：存在能复现的同步逻辑缺陷，也存在剩余的卡顿和内存高峰来源。未确认会持续无限增长的内存泄漏；下文将处理高峰、异常长期留存与泄漏分开。P1 表示优先修复，P2 表示随后处理。

1. **P1 · 超大文本先完整读取，之后才检查大小限制。静态确认。**

   触发：从编辑器、日志查看器或表格复制远超设置上限的文本。即使设置只允许 1 MB，程序也已经把整份文本读进内存。MyGo 的 `ReadText` 通过主线程调用原生接口；Windows 实现还会复制原始字节、建立 UTF-16 数组并转成字符串。结果可能是 UI 停顿和大幅内存上涨，随后才提示超限。

   位置：[board_mygo.go](../internal/clip/board_mygo.go#L84)；本地依赖 `mygo@v0.5.5/clipboard.go:87`、`internal/windows/system.go:126`、`internal/darwin/system.go:28`。

   修复：新增带字节预算的原生文本读取，在复制到 Go 和完整转码前检查长度，转码过程中也限制输出；Windows 原生读取放到固定后台线程。macOS 的数据提供方可能在读取调用内部阻塞，应单独记录耗时，核对可以移出主线程的接口范围。图片的 macOS `dataForType:` 仍在主线程，后台解码并不能消除数据提供方迟迟不返回造成的停顿。

   验收：超限文本只产生受限分配；复制期间仍能操作窗口。尚未用真实系统剪贴板注入超大文本，以免影响用户当前内容。

2. **P1 · 历史保存阻塞采集链路，会漏掉中间复制；接收链路也被历史与 UI 回调阻塞。采集丢失已复现。**

   触发：历史目录在慢磁盘上、系统磁盘繁忙、正在清理大量历史，或长文本落盘较慢时，连续复制 A、B、C。监听器同步调用 `HandleLocal → onNotice → hist.Add`，长文本保存包含 `Sync`；处理 A 时不再采集 B，即使 B 的稳定时间已经超过防抖窗口，最终也可能只留下 A、C。

   位置：[board.go](../internal/clip/board.go#L41)、[window.go](../cmd/snapover/window.go#L350)、[text.go](../internal/history/text.go#L27)、[session.go](../internal/sync/session.go#L351)。

   远端 `readLoop` 同步执行图片解码、剪贴板发布、历史保存与 UI 通知，这期间也不能继续消费确认、心跳和文件帧。长时间阻塞会导致确认延迟，严重时被判为超时。

   修复：采集、持久化和 UI 通知分开；使用同时限制条数与总字节数的任务队列，满时给出明确结果。网络读取与内容处理分离，保持处理顺序，实际处理完成后再确认；不能简单为每条内容无限启动 goroutine。

   验证：临时测试让消费回调阻塞，B 稳定 100 ms、防抖 5 ms，实际只收到 `[A C]`。

3. **P1 · 内容哈希去重会吞掉真正的新复制。两种路径均已复现。**

   场景一：本机复制 A 并发送，随后收到远端 B，再在本机重新复制 A。远端写入没有重置 `lastHash`，新的 A 会被当作上次本机复制而直接丢弃。

   场景二：收到远端 A 后，5 秒内先复制 B，再主动复制 A。`EchoGuard` 仅凭内容哈希和时间，仍把新 A 当作远端回声。

   位置：[engine.go](../internal/sync/engine.go#L107)、[echo.go](../internal/clip/echo.go#L44)。

   影响：新内容未发送、未新增历史，`localActive` 也没有更新，随后远端内容还可能覆盖这次本地复制。新增“复制并同步”的显式请求会绕过这两项去重，但普通自动同步仍受影响。

   修复：以剪贴板 generation 和自身写入标记判断回声；内容相同不能直接等同于事件相同。远端写入使本地去重基线失效。将上述两个场景加入正式回归测试。

4. **P1 · 暂停同步不会撤销已排队的内容。已复现。**

   触发：弱网、发送大图或有积压时点击“暂停同步”。`SetPolicy` 只改变后续入队策略；发送循环检查确认期限，却不检查当前暂停状态。暂停前尚未开始发送的文本和图片仍可在之后发送。切换手动模式也有同类队列语义问题。

   位置：[engine.go](../internal/sync/engine.go#L162)、[session.go](../internal/sync/session.go#L314)、[clipboard_result.go](../internal/sync/clipboard_result.go#L92)、[copy.go](../internal/sync/copy.go#L17)。

   修复：暂停时撤销未开始的剪贴板任务并释放内容；写出前重新验证策略或任务代次，同时给等待确认的任务返回取消结果。已发往网络的字节无法撤回，应明确在途任务的处理规则。文件主动发送保持现有独立语义。

5. **P1 · 设置保存失败时，界面显示与实际同步状态不一致。已复现。**

   触发：数据目录不可写、磁盘满或设置替换失败，然后切换暂停、只同步文本或图片上限。`saveSettings` 先改 UI 和内存配置，保存失败直接返回；引擎未更新，开关也未回滚。尤其可能出现界面看起来暂停了，实际上还在同步。

   位置：[window.go](../cmd/snapover/window.go#L821)。

   修复：保存前保留旧配置，失败时同步回滚 UI 和内存状态，成功后再提交引擎策略；复用已有 `saveSyncMode` 的处理方式。提示应说明设置未生效。

6. **P2 · Windows 图片重复解码，而且暂停接收时仍先准备原生图片。后者已复现，Windows 峰值未实测。**

   触发：Windows 回贴历史大图或接收大图。`PNGForPaste` / `FromPNG` 先完整解码，随后 `prepareNativeImage` 再解码以生成 DIB。准备阶段还同时存在解码像素、原生 DIB 和 PNG，单个解码额度不等于整个进程的内存预算。

   位置：[item.go](../internal/clip/item.go#L121)、[image_clipboard_windows.go](../internal/clip/image_clipboard_windows.go#L113)、[engine.go](../internal/sync/engine.go#L236)。

   `deliverFrom` 在检查暂停、本地复制优先和会话是否有效之前调用 `PrepareRemoteWrite`。因此本来要拒绝或只存历史的图片，也可能先做一次昂贵的 Windows 原生准备。

   修复：昂贵准备前做一次快速策略检查，发布前仍做最终检查以防状态变化；将 PNG 校验与原生缓冲准备合并为一次解码并明确所有权。处理预算应覆盖原生缓冲的生命周期，避免仅限制解码函数并发。

   验证：假剪贴板测试确认暂停状态仍执行原生准备。Mac 上现有 2000×2000 历史粘贴基准，单次 `PasteItem` 约 10 ms、累计分配 15.4 MiB；这尚不包含 Windows 后续的再解码与 DIB 分配。

7. **P2 · 未完成图片没有独立超时，可长期保留最多约 20 MiB。静态确认，有界留存风险。**

   触发：对端传来图片头和至少一个分片，之后停止该图片传输，但心跳仍正常。例如对端实现异常，图片任务中断却未关闭会话。第一个分片按声明总大小分配缓冲；只要没有下一张图片、结束帧或断线，`asm` 就一直保留。

   位置：[session.go](../internal/sync/session.go#L257)、[session.go](../internal/sync/session.go#L434)。

   修复：为图片组装记录进度时间和独立截止时间，超过期限释放缓冲并返回失败；心跳不能延长图片任务期限。需保证没有新数据帧时也会触发清理。

   单会话只有一个组装器，不能据此宣称无限泄漏。正常对端发送失败会关闭连接，通常能回收。

8. **P1 · 历史删除与日志持久化之间存在掉电一致性窗口。静态风险，未做断电复现。**

   触发：删除、容量清理或清空后，在日志尚未持久化时掉电或发生系统崩溃。`persistLocked` 普通追加不 `Sync`，却已经返回成功，调用者随后删除正文和图片；恢复时可能回到旧索引，出现记录还在但内容文件已丢失。普通进程退出不等于断电，不能用 kill 进程测试证明这一点。

   位置：[journal.go](../internal/history/journal.go#L68)、[store.go](../internal/history/store.go#L302)。

   修复：至少在物理删除前保证对应日志已持久化。可以后台批量提交，提交完成后再删除资源与报告完成；快照替换和日志截断还应按平台确认目录元数据的持久化顺序。不能仅依赖每 256 次操作或 1 MiB 时的快照阈值。

9. **P2 · 复制并同步的 2 秒期限包含稳定等待和完整采集处理。静态确认。**

   触发：手动模式下用快捷键复制大图，但数据提供方、共用图片处理额度或解码耗时超过 2 秒。请求只在 `HandleLocal` 处理结果时认领，届时可能已经过期；实际复制成功仍提示“未复制到新内容”，该内容只进入本机历史。自动模式下，迟到的采集还可能走普通自动发送，使失败提示与实际结果不一致。

   位置：[copy.go](../internal/sync/copy.go#L29)、[engine.go](../internal/sync/engine.go#L71)、[copy_sync.go](../cmd/snapover/copy_sync.go#L39)。

   修复：区分“等待新剪贴板 generation”与“处理已观察到的 generation”；在观察到新 generation 时认领请求，后续采集使用独立的有限处理期限并支持取消，超时提示区分未复制与处理超时。避免单纯无限延长等待。

10. **P2 · 历史损坏会使整个应用无法启动，缺少降级恢复入口。静态确认。**

    触发：历史索引无效或日志整条记录校验失败。`history.Open` 返回错误，主程序直接退出，因此设备连接、文件发送和设置恢复入口也不可用。

    位置：[main.go](../cmd/snapover/main.go#L129)。

    修复：保留损坏文件，提供恢复入口；可在明确显示历史不可用的状态下启动基本功能。涉及“只存历史”的接收冲突，必须明确返回保存失败，不能伪报成功；不要悄悄清空用户历史。

验证与边界：

- `go test ./...` 首次未全绿：`TestLoggerWritesFileWithoutConsole/true` 缺少启动诊断。单独 `-count=10` 复跑有两轮失败。测试子进程在异步 Breadcrumb 写出前退出，没有调用正常退出路径的 `MarkClean`；建议测试退出前显式 flush/MarkClean，避免靠 Sleep。现阶段不能把这个测试失败直接认定为应用必然丢日志。
- `go test -race ./internal/... ./cmd/... -count=1` 通过；没有检测到这些现有测试覆盖范围内的数据竞争。它不能排除上文的状态机错误。
- `go vet ./internal/... ./cmd/...` 通过。
- 使用临时 Go overlay 添加 6 个目标断言，全部复现预期行为不成立：慢消费丢 B、远端写入后本地重拷、远端哈希 TTL 误判、暂停后排队项仍可发、保存失败未回滚、暂停接收仍原生准备。临时测试未写入源码目录。
- 4000×10000 合成图接收基准在 Apple M4/macOS arm64 上单次约 262 ms，累计 Go 分配约 157 MiB。这是算法处理与测试剪贴板路径，既不是 UI 停顿时间，也不是 RSS、保留堆或泄漏量。
- 没有进行 Windows 实机运行、两设备弱网验收、数小时驻留或原生堆跟踪；原生内存是否持续增长仍需这些验证。没有修改系统通用剪贴板或用户历史。
- 已有缩略图 LRU、通知数量上限、历史粘贴单任务、预览关闭清理和窗口销毁逻辑，不能仅因曾出现内存高峰就认定这些旧问题仍然存在。

建议修复次序：先修复去重、暂停队列与设置回滚，以及删除前持久化；随后处理超大文本读取和采集/落盘解耦；再处理图片重复解码、组装超时、复制请求期限与历史恢复入口。内存验收同时观察 Go 存活堆、原生内存和 RSS，区分操作完成后的正常缓存与每轮操作后持续抬升的基线。
